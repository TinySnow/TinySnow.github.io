# 微信公众号文章转博客格式：工作约定

## 目的与适用范围

本文件记录从现有博客文章中归纳出的稳定格式，供后续开发“微信公众号文本转博客 Markdown”工具时使用，避免在多轮工作中遗漏或擅自改变既有写作样式。

本文件适用于 `assets/` 目录及其子目录。转换脚本如放在此处，应遵守以下约定。若后来改为在仓库根目录新建 `scripts/`，应把本文件中的相关规则同步到该目录的 `AGENTS.md`。

## 博客文章的标准骨架

文章通常采用以下顺序：

```markdown
# 文章标题

## 写在前面

<p style="color:#0f4c81; text-align:center; font-weight:bold; font-size:larger;">字数 字 | 标签一 | 标签二</p>

## 正文

　　正文第一段。

　　正文第二段。

<br />

　　南国微雪 Miyuki

　　YYYY 年 M 月 D 日

## 写在后面

　　可选内容。

## 封面图

![](封面图地址)

> 摄影师・画师 | 作者或来源
>
> 图源 | 平台或来源
```

其中 `## 写在后面` 是可选章节，其余部分在参考文章中均存在。

## 各部分格式规则

### 标题与文件名

- 正文第一行使用一级标题：`# 文章标题`。
- 文件名通常取文章标题并以 `.md` 结尾，但会为了路径简洁而省略标题中的部分空格。例如标题中的 `llm` 或年龄前后可能有空格，文件名中没有。
- 不要擅自把英文缩写改成大写；参考文章使用 `llm`。
- `src/SUMMARY.md` 中展示的标题可以包含额外的视觉标记，例如重点文章前的 `⭐️`；该标记不一定属于正文标题或文件名。

### “写在前面”

- 固定标题为 `## 写在前面`。
- 第一项通常是单行 HTML 段落，样式字符串应保持为：

  ```html
  <p style="color:#0f4c81; text-align:center; font-weight:bold; font-size:larger;">……</p>
  ```

- 内容格式通常是 `字数 字 | 标签一 | 标签二 | …`。
- 字数与标签之间、标签彼此之间使用半角空格包围的竖线：` | `。
- 字数应以最终正文为准计算，不能直接照搬微信公众号可能显示的旧字数。具体计数口径需要结合待提供的微信导出样本和用户期望再确定。
- 如果文章另有阅读提示，可在标签行后增加普通居中 HTML 段落，例如：

  ```html
  <p style="text-align:center;">阅读提示。</p>
  ```

### 正文

- 固定标题为 `## 正文`。
- 普通中文正文段落以两个全角空格开头，即两个 U+3000 字符：`　　`。
- Markdown 源码中，各段之间保留一个空行。
- 不要把两个全角空格替换为四个半角空格、制表符或 HTML `&emsp;`。
- 场景转换、较强的语义停顿或文末署名前，使用独占一行的 `<br />`；其前后各空一行。
- 保留有意义的 Markdown 行内格式，包括：
  - 加粗：`**文字**`
  - 下划线：`<u>文字</u>`
  - 加粗与下划线组合：`<u>**文字**</u>`
  - 链接：`[文字](URL)`
- 正文可以出现编号、引用内容和强调段，不应为了统一外观而删除原有语义格式。
- 中文与英文缩写、阿拉伯数字之间的空格，应尽量沿用作者在现有文章中的写法，不做激进的自动排版或内容润色。
- 转换工具的职责是格式迁移，不应未经要求改写措辞、修正观点或重组文章结构。

### 署名与日期

- 正文结束后通常先放一行 `<br />`。
- 署名固定为：`　　南国微雪 Miyuki`。
- 日期单独成段，格式通常为：`　　YYYY 年 M 月 D 日`。
- 署名和日期均以两个全角空格开头，二者之间空一行。
- 个别文章在日期之后还有地点或情境说明，应作为独立段落保留，并同样使用两个全角空格缩进。

### “写在后面”

- 此章节可省略。
- 存在时固定标题为 `## 写在后面`，位置在署名日期之后、`## 封面图` 之前。
- 内容可能是补充说明，也可能是正文配图；不得假设它一定是文字。

### 封面图

- 固定标题为 `## 封面图`。
- 封面图片使用 Markdown 图片语法：`![](URL)`。
- 当前文章的图片一般托管在 `https://raw.githubusercontent.com/TinySnow/GithubImageHosting/main/blog/articles/literature/` 下，但转换工具不应凭空生成文件名或 URL。
- 图片后使用 Markdown 引用块记录署名：

  ```markdown
  > 摄影师・画师 | 作者或来源
  >
  > 图源 | 平台或来源
  ```

- `摄影师・画师` 中间使用的是日文间隔号 `・`。
- 作者和图源必须来自用户提供的信息或可验证的现有数据；缺失时应保留待填写项或明确提示，不能猜测。

### SUMMARY 条目

- 新文章最终应加入 `src/SUMMARY.md` 的“文章与写作”对应列表。
- 链接路径相对于 `src/SUMMARY.md`，通常形如：

  ```markdown
  - [展示标题](生活碎笔/文章与写作/文件名.md)
  ```

- 必须保持所在列表的现有缩进。是否添加 `⭐️` 由用户决定，不应由脚本根据内容自行判断。
- 更新前应检查是否已有同名标题或同一路径，避免重复条目。

## 转换工具的预期职责

收到微信公众号文本编辑器复制出的真实样本后，再确定输入解析方案。理想工具至少应做到：

1. 接收复制出来的文本或保存后的输入文件。
2. 清理微信公众号引入、但博客不需要的排版噪声。
3. 尽量保留段落、粗体、链接、引用和必要的换行语义。
4. 按上述骨架生成博客 Markdown。
5. 补齐或提示填写标题、标签、日期、封面图地址、图片作者和图源。
6. 计算正文的字数，并生成“写在前面”的居中标签行。
7. 生成安全的目标文件名，并可选地更新 `src/SUMMARY.md`。
8. 写入前展示或输出转换结果，避免静默覆盖已有文章。

## 当前转换工具

当前实现为 `assets/convert-wechat-article.ps1`，默认把 `assets/wechat-origin.md` 转换到 `src/生活碎笔/文章与写作/`，并从一级标题、文章末尾标题、显式参数或剪贴板取得标题。

在仓库根目录运行：

```powershell
.\assets\convert-wechat-article.ps1
```

也可在资源管理器中右键 `convert-wechat-article.ps1` 并选择“使用 PowerShell 运行”。脚本的默认输入、输出路径始终相对于仓库根目录解析；从资源管理器启动时，成功或失败信息会保留在窗口中，按 Enter 才会关闭。

该 `.ps1` 文件必须保存为 **UTF-8 with BOM**。资源管理器右键运行使用 Windows PowerShell 5.1，它不能可靠解析带中文的 UTF-8 无 BOM 脚本；修改脚本编码时不得移除 BOM。

输入文件可以没有一级标题。无标题时，先在微信公众号中复制文章标题，再运行上述命令；工具会读取剪贴板中的单行文本，将其补为一级标题，并用它生成文件名。标题不需要粘贴进 `assets/wechat-origin.md`。

如果不希望读取剪贴板，也可以显式传入标题：

```powershell
.\assets\convert-wechat-article.ps1 -Title "文章标题"
```

也可以把未经 Markdown 格式化的标题粘贴为整篇输入的最后一个独立文本行。工具会把该行从末尾移走，自动补成开头的一级标题。不要把标题无分隔地直接拼在图源行之后，例如 `> 图源 | Unsplash文章标题`；这种文本没有可靠的标题边界，无法安全自动拆分。总体上，推荐使用剪贴板方案，因为复制标题后无需再次粘贴。

也可以指定其他输入文件或输出目录：

```powershell
.\assets\convert-wechat-article.ps1 -InputPath .\其他输入.md
.\assets\convert-wechat-article.ps1 -InputPath .\其他输入.md -OutputDirectory .\converted
```

工具执行以下规范化操作：

- 从首个一级标题读取文章标题，并用完整标题作为 Markdown 文件名。
- 输入没有一级标题时，依次尝试 `-Title`、文章末尾的独立标题行、剪贴板中的单行标题，并自动补齐一级标题。
- 如果封面图源信息之后还有一个独立的普通文本行，则把该行视为末尾标题；标题不需要带 `#`。
- 把 `> 字数 字 | 标签` 转换为博客所用的居中蓝色加粗 HTML。
- 把正文中两个以上连续空白行表示的场景分隔转换为 `<br />`。
- 在 `南国微雪 Miyuki` 署名前补充缺失的 `<br />`。
- 把微信导出的封面语法 `![img](URL)` 规范化为 `![](URL)`，保留原 URL。
- 默认拒绝覆盖同名文章；只有明确传入 `-Force` 才会覆盖。

当前工具不会自动下载或迁移微信图片，不会自动更新 `src/SUMMARY.md`，也不会修改文章内容和标签。这些操作如有需要，应在用户明确要求后另行实现。

## 博客元数据生成工具

- `assets/generate-last-updated-md.sh` 根据暂存区或 Git 提交范围生成 `src/last-updated.md`，并保留最近若干次更新记录。
- `assets/generate-rss.py` 根据 `RSS_GIT_RANGE` 或最近一次提交生成仓库根目录的 `rss.xml`。
- RSS 生成器只使用 Python 标准库，不需要安装项目级 Python 依赖。
- GitHub Actions 直接调用上述两个脚本；调整文件名、参数或输出位置时，必须同步修改 `.github/workflows/mdbook.yml` 和 `autopush.sh` 中的说明。

本地按提交范围验证时，可在仓库根目录运行：

```bash
bash ./assets/generate-last-updated-md.sh --range "HEAD^..HEAD"
python3 ./assets/generate-rss.py --git-range "HEAD^..HEAD"
```

## 尚待微信样本确认的事项

在看到用户提供的真实文件之前，不要预先锁定以下实现：

- 输入究竟是纯文本、HTML、富文本片段、Markdown，还是其他格式。
- 微信编辑器复制时如何表达粗体、链接、图片、引用、空段和软换行。
- 前言、封面图和图源信息在输入中是否存在，以及它们能否可靠识别。
- 字数的统计口径是否包含标点、数字、英文、标题、署名或“写在后面”。
- 工具采用 PowerShell、Python、Node.js，还是剪贴板快捷方式。
- 是否自动写入文章文件与 `SUMMARY.md`，或只生成待审核的 Markdown。

应先检查样本的真实结构，再选择依赖最少、在当前 Windows 环境中最方便重复使用的实现方式。

## 验证要求

- 至少用用户提供的原始微信样本完成一次端到端转换。
- 将结果与上述参考文章逐项对照：章节顺序、空行、全角缩进、HTML 样式、署名日期、封面信息和 SUMMARY 路径。
- 检查生成文件的 UTF-8 编码和中文文件名。
- 如工具会修改 `src/SUMMARY.md` 或覆盖目标文件，必须提供预览、确认或防覆盖机制。
- 不以肉眼浏览代替必要的脚本测试；同时也要人工检查生成 Markdown 的可读性。
