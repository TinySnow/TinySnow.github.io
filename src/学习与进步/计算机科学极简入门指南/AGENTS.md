# AGENTS.md

本文件是《计算机科学极简入门指南》系列的合作写作规范。

**任何 agent 在新增、修订本系列文章（尤其是“计算机组成原理”分册）之前，请先完整阅读本文件，并严格遵守，以保证不同 agent 产出的文本风格一致。** 若本文件与其它说明冲突，以本文件为准。

---

## 一、总体基调

- 面向**零基础**读者，自底向上，一步一步把零件搭起来：先造小部件，再用小部件拼大部件。
- **摒弃术语堆砌**：任何术语首次出现时，先用生活化语言把它讲明白，再给出名称与英文缩写，例如“程序计数器（PC，Program Counter）”。
- 语气**介于口语和书面语之间**：亲切、直接、有耐心，常用“我们”“你”，可以设问、可以打比方，但不油滑、不卖萌、不用 emoji。
- 不居高临下，也不神化知识；像一位耐心的同伴，带着读者边走边造。
- 可在合适处呼应本系列反复强调的四句话，但不要生硬堆砌：
  - 懒是人类进步的第一动力。
  - 在计算机科学里，没有什么问题是加一层解决不了的。
  - 人类所有知识都来源于好奇心和解决问题。
  - 所有庞大学科知识体量均由积累而成，不会一蹴而就。

## 二、章节结构（必须齐全，顺序固定）

1. `# 标题`：只写章节名，**不要**写“第X章”。
2. `## 复习`：用 `- 主题：一句要点` 的无序列表，回顾紧邻的前几章（通常 3 条，早期章节可更少）。**每一条都必须以“主题＋全角冒号 `：`”开头**，例如 `- 补码：补码是反码加 1，能统一加减法且只有一个零`；**不要写章号**，也不要只写一句没有主题前缀的话。这是全系列最容易反复漏掉的一点：新建分册或续写章节时，复习条目常常写成没有“主题：”的普通句子，务必逐条核对。
   - **复习必须严格回顾“紧邻的前三章”（滑动窗口），不得因为主题相关就跳到更早的章节。** 具体规则：第 N 章的复习恰好是第 N-3、N-2、N-1 章各一条，且按此先后顺序排列；第 N-3 章对应第一条，N-2 对应第二条，N-1 对应第三条。
   - 跨分册时同样取前一册的最后三章（例如某分册第 1 章的复习，取上一分册的倒数第 3、2、1 章）。
   - 每一章只应有一份标准表述（`主题：要点`），其它章节引用它时保持同一措辞，避免同一章在不同地方被总结成不同句子。
   - 若某章的主题恰好不在前三章之列（例如它按主题应该回顾更早的先修章），也**仍然遵守滑动窗口**，在正文里另行交代先修关系，而不是在复习里回跳。
3. `## TL;DR`：2~4 条结论式短句，是读完整章后应当记住的东西，不是目录。
4. `## 正文`：写法见第三节。
5. `## 小结`
   - `### 知识点`：本章要点，用无序列表。
   - `### 参考资料`：编号列表，每条格式为 `[名称](链接)：一句话说明`。
   - `### 推荐`（可选）：视频等延伸材料。
   - `### 思考题答案（仅供参考）`：对照思考题逐一作答。
6. `## 协议`：固定文案，原文照抄：
   `本作品采用[知识共享署名-非商业性使用-相同方式共享 4.0 国际许可协议](https://creativecommons.org/licenses/by-nc-sa/4.0/deed.zh)进行许可。`
7. `## 封面图`：一行 `![](图床链接)`，随后一行 `> 设计师 | 南国微雪`。

补充：**思考题**插在正文中，格式为居中加粗的 ` **思考题** `，后跟一个引用块 `> 　　……`；一章 1~2 道，必要时可编号为“思考题 1/2”。

## 三、正文写法

- 每个自然段以两个全角空格 `　　` 开头。
- 开头先承接上一章，或抛出一个问题、需求、生活场景，说明“为什么现在要讲这个”。
- 由问题驱动，基本节奏是：**提出问题 → 给直觉或类比 → 再形式化 → 落到电路或代码**。
- 善用生活类比（保险箱、楼梯双控开关、快递柜、翻译官……），但比喻之后一定要回到技术本体，不能停在比喻。
- 推导要一步一步来，宁可多写一句，也不要跳步；关键结论用 **粗体** 点出。
- 章末常用一句话预告下一章，形成连贯的叙事，例如“这就引出了下一章的主角——补码”。
- 可用 `###`、`####` 分级小节，但不要层层嵌套太深。
- 图示优先用图床图片；没有图片时，用 ASCII 示意图兜底。

## 四、语言与标点（重点，提交前务必自查）

- **正文一律使用中文引号 `“ ”`（双引号）与 `‘ ’`（单引号），并且前后必须成对匹配。**
- **禁止在正文中出现直角引号 `"`**；直角引号只允许出现在代码块、行内代码、命令、URL、HTML 属性等技术示例中。
- 引号嵌套：外层 `“ ”`，内层 `‘ ’`。
- 使用全角标点（，。：；？！、）；中文与拉丁字母、数字之间加空格，如 `1 KB`、`PC 保存`。
- **不使用任何 HTML 标签**（`<sub>`、`<sup>`、`<span>`、`<u>` 等一律不用）：
  - 上下标用 Unicode 字符：`²`、`³`、`ⁿ`、`₁₀`、`₂`。
  - 取反用组合上划线 `A̅`，也可写成 `~A`。
  - 强调统一用 Markdown 粗体 `**…**`。
- 数学符号沿用离散数学与布尔逻辑：与是乘法（可省略乘号）、或是加法、异或是 `⊕`。
- 代码、指令、二进制串、文件名等一律用行内代码 `` `…` ``。
- 加粗和斜体等 markdown 格式标点两侧，务必留有空格，以便不同 markdown 解析器都能表现出一致的行为：`前文。 **内容。** 后文。`远优于`前文。**内容。**后文。`。

## 五、内容与引用规范

- **正文中不写“第X章”**，改用概念式表述：`前面讲有符号数时`、`上一章`、`下一章`、`前面那个累加器`。这样章节增删调整时无需回头改引用。
- 需要跨章跳转时，用相对 Markdown 链接，例如 `[前面讲过的触发器](./第二十章：触发器.md)`；mdBook 会自动把 `.md` 改写为 `.html`。
- 不引入超出当前进度的知识；若必须提前提及，注明“后面会讲”。
- 思考题要能运用本章知识，并尽量把前面几章串起来，不要考死记硬背。

## 六、去 AIGC 味（硬性，写完必查）

早期章节由 AI 起草，最常见的毛病不是术语写错，而是三样：一句话里并排放两条线、用套话充当推进、读完记不住这一章在讲什么。以下五条针对这三样。它们与《学海计划》的规范同源，已按本系列的文体改写：本系列允许代码块、图示与小节标题，其余照旧。

### 1. 推进方式：一条线走到底（硬性）

人读东西时，脑子里只跑得动一条线。技术讲解更该如此——造零件本来就是一步接一步的过程，中途岔开，读者就接不回原来的线了。

1. **一段话只走一条线。** 先把一个点讲透，再转下一个，不要在同一段里来回横跳。
2. **要对比，也顺着走。** 先讲 A，A 讲完再讲 B。不要写“既是 A 又是 B”“不仅……而且……”这种两头都够、两头都不到的句子；顺序推进（先……再……）和因果推进（所以……因为……）更像人说话。
3. **中途别插不重要的话。** 真要插（补一个数据、补一个反例），插完**在原处接回去**。本章允许的中断只有两种：括号旁注，和新开的小节。
4. **同时给两条路，要有明确理由。** 确认读者确实站在岔路口（两种实现各有取舍、需要他自己选），才并排给出；否则一次只讲一条。

**自检**：把正文画成一条箭头链（A→B→C→D），而不是一棵树。某段同时抛出两个以上并列说法，或连续几段各抛几个，就是广度搜索，得改成一条线走到底。

**例**（同一条信息，两种走法）：

- 广度：“进程看到的地址并不是物理地址，而是一张操作系统发下来的映射表。”读者一次要接两件事：不是物理地址、是映射表。
- 深度：“进程看到的地址，是操作系统发下来的一张映射表。表后面才对应真正的物理内存。”先把“映射表”这条走完，再转到它对应什么。

### 2. AI 腔硬性禁表（绝对不得出现）

以下表达任何情况下都不许写进正文、小标题、`## TL;DR` 与 `## 小结`；写完先搜一遍，命中就改。

**一、特定短语**

- “不是 X，是 Y”“不是 X，而是 Y”
- 堆砌形容词，如“用最直白、最不绕弯子的方式讲清楚”
- 对话式讨好话术：“你太懂了”“稳稳接住你”

**二、承诺式与宣言式套话**

- “我不是要……而是要……”“不是为了……而是基于……”“不是简单的……而是深刻的……”
- “我这就用最 XX 的方式给你解释／说明／拆解”
- “保证你一听就懂”“一听就懂”“最直白”“最不绕弯子”“掰开了揉碎了”
- “深度拆解”“底层逻辑”（本系列里“底层”是技术词，“底层的门电路”“底层实现”照写；禁的是拿它当修辞，如“搞懂底层逻辑，就掌握了整个计算机”）
- “通往……的黄金钥匙”
- “这不仅仅……更……”

**三、悬空修辞与通货膨胀的比喻**

- “达摩克利斯之剑”“历史的十字路口”“人性贪婪的深渊凝视”
- “一场……的博弈”“一次对……的凝视”
- 用“危言耸听”这类贩卖焦虑的大词给段落开场

**四、强迫式干货感连词堆叠**

- “今天我必须要把这个事情给大家说清楚”
- “我们把这个概念……”
- “知道了……就拥有了……”

**“不是 X，而是 Y”怎么改**：它被硬禁，但句子里承载的信息不能丢（可能是在纠正一个真实误解，也可能两半都有实义）。改法是把话说直：

- 说“错误发生在保存阶段”，不要写“不在读取阶段，而在保存阶段”。
- 说“虚拟地址要先经 MMU 翻译”，不要写“不是直接访问物理内存，而是先翻译虚拟地址”。
- 确实需要对比时，把否定半句挪到后面、单独成句：“重点在保存阶段。读取阶段没有出错。”

**登记**：正文里出现禁表之外的 AI 腔（例如“值得注意的是”“不难发现”“这意味着”在同一篇里反复出现），在提交信息里记一行，不要写进正文；这类句式同一篇里出现一次就够。

### 3. 结构清晰（硬性）

`## TL;DR` 和 `## 小结` 是结论清单，不等于正文结构清晰——读者在**读正文的过程中**就要能看出这一章分几步、每步在做什么。三条要求：

1. **开篇让读者知道这一章要造什么、往下分几步。** 可以是路线图（“往下分三步：先……再……最后……”），也可以由上一章留下的问题直接带出。别让读者读到中段才知道在干什么。
2. **每一步的开始要能看出来。** 用 `###` 小标题、加粗领起句、序号都可以；一层讲完再开下一层，同一层的意思不要散在章里反复出现（前面说过、中间又说、小结再说一遍，就是串场）。
3. **章末要能一句话说清结论。** 读者读完能回答“所以呢”。

**要避免的两件事**：一是每章套同一个骨架（这章用路线图，下一章就换序号或提问切入，别一个模子刻到底）；二是用手段掩盖空结构——加了小标题却没有对应的内容层次，路线图承诺三步、正文只有两步，比不加更糟。

**自检**：通读一遍，回答——这章分几步？每步在讲什么？结论是什么？答得出来才算过。

### 4. 多样性与节奏（软性）

- **长短句交错。** 连续三句都超过四十字就要拆；反过来，连着五六个短句也会读得发飘。
- **句式换着来。** “不是……而是……”“值得注意的是”“不难发现”“这意味着”这类句式，同一篇里出现一次就够；同一段里连着两句用同一句式，改掉一句。
- **用词别回环。** 同一个意思别反复用同一个词，同一个连接词别承包全章。
- **推进方式也要多样。** 例子、数字、反例、边界、换个角度复述，轮着来；不要每段都是“提出判断—补一个限定”。

**一句话判据**：出声念一遍，念到一半要停下来回一口气，或者得回头重排一遍句子，这句就太长了。默读会自动替你把句子补顺，问题就漏掉了。

### 5. 收尾不升华、不喊口号

章末可以预告下一章，但不要打鸡血、不要替读者激动、不要做道德审判。工程上的取舍就把取舍摆出来；结论留边界（“视具体实现而定”“这一层还有代价”），不要写成口号。

## 七、文件与构建

- 章节文件名格式：`第X章：标题.md`（冒号为全角）。
- **文件名不得包含 ASCII 空格**（会导致 mdBook 解析 `src/SUMMARY.md` 失败）。确需空格时，在 `src/SUMMARY.md` 中把空格写成 `%20`。
- 新增或重命名章节后，同步更新 `src/SUMMARY.md`（只改本系列相关条目，不要动其它分册）。
- 提交前在仓库根目录执行 `mdbook build`，确认构建通过。
- 改动范围限定在《计算机科学极简入门指南》目录内，不要修改其它分册与无关文章。
